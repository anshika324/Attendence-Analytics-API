Also note anything you looked at and decided was **not** a defect, and why:

1. **`emp_code` being a string rather than MongoDB `ObjectId`**:
   We examined whether `emp_code` should reference an `ObjectId`. As specified in `DATA_MODEL.md` and `PROBLEM_STATEMENT.docx`, `emp_code` is a customer-assigned business code (e.g., `EMP0001`) that serves as the unique natural identifier across all endpoints. `_id` is purely internal to MongoDB and must never appear in API requests or responses. Keeping `emp_code` as the natural key is intentional and correct.

2. **Absence of an `id` field in attendance records**:
   We verified whether attendance records should have an `id` property. The API contract explicitly defines an attendance record by the natural compound key `(emp_code, date)`. The starter's addition of `doc["id"] = str(res.inserted_id)` was a defect, and removing it matches the `AttendanceRecord` schema.

3. **Storage of dates and shift times as strings**:
   `date` (`"YYYY-MM-DD"`) and shift times (`"HH:MM"`) are stored as plain strings in MongoDB. We evaluated converting them to BSON datetimes, but confirmed that storing them as calendar strings is intentional to avoid accidental timezone distortion. Instants (`punch_in`, `punch_out`, `created_at`, `history.at`) are stored as BSON datetimes and converted to epoch milliseconds at the API boundary.
